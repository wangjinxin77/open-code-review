通用 Agent

越找越多

Cursor Agent 这类通用循环，再追问一轮，往往会再翻出一批评论。文件覆盖变了，行号对不上刚才那一版，真问题和顺嘴一说混在一起。

  1. 大变更集里，它会挑着看。
  2. 报出来的位置经常漂。
  3. 提示词动几个字，结论就换一副面貌。
Open Code Review

同一 diff 再跑，文件集不动

哪些文件进入审查，由过滤器决定，不由模型当场发挥。评论若被 diff 事实直接打脸，会被拿掉；同一份 diff 再跑不会换一套审查范围。

  1. 进不进审查，程序先算完。
  2. 行号由 existing_code 片段匹配算出，模型不报行号。
  3. 核查者只能删被证伪的评论，不能另起一条。

模型可以是同一个。变的是谁来约束流程。

Cursor 只是通用 Agent 发散的直观举例；全篇量化对照统一用 Claude Code（见数据页）。

确定性代码 LLM 推理 模型在场，边界由程序规定
不交给模型决定
这个文件看不看 用哪一条规则 行号交给模型填写 被 diff 证伪的评论留不留 核查者能不能新写一条

03 · 职责分离全场重点之一

谁做什么，比提示词写什么更先决定质量

环节谁负责为什么不能混
文件筛选、噪声目录、五重门、超大 diff 拦截 确定性工程 漏看和误放不能靠模型自觉。同一份 diff，文件集应可复现。
规则匹配：临时 > 项目 > 用户全局 > 内置 确定性工程 标准先于推理。Replace / Merge 是配置，不是现场挑选。
语义文件分组：相关文件捆成一组，每组 ≤10，按 token 预算拆分 GROUPING_TASK（LLM 调用） 只喂文件元数据不含 diff。分组失败 / 空 / 仅 1 文件时退化为每文件一组。
按组并行分发、组间上下文隔离、有界并发 确定性调度 每组独立 goroutine + 独立消息缓冲，组内文件共享同一上下文。默认并发 8。
读上下文、追调用、判断是否缺陷 LLM 子 Agent 语义只有模型能做。工具集审查专用，输出有上限。
评论行号 确定性匹配为主 模型只交 existing_code；程序匹配出行号，失败才 RE_LOCATION_TASK。
评论是否被 diff 事实打脸 独立 Reflector 只判事实真假，不判价值高低。只能删，不能新写。

03 · 实现 · 语义分组流水线 ④/⑧ · GROUPING_TASK · 每组 ≤10 文件

相关文件捆成一组，再按组并行审查

$ GROUPING_TASK
# 只喂文件元数据，不喂正文 diff
in  : N 个文件的 {path, 变更规模, 命中规则}
out : 相关文件捆成组，每组 ≤10
→   每组并行起一个子 Agent（⑤）

分组阶段不吃正文，元数据很小，token 成本可控；真正的正文只在子 Agent 里按需读。这一步把「谁该和谁一起被审」定下来——相关文件捆进同一对话，结构强相关的依赖免费共享上下文。

README 归到「确定性工程」，实现却是一次 LLM 调用。 它是流水线里被前后代码夹住的那一段不确定：分组错了不会崩，只是把本该一起审的文件拆散，各子 Agent 仍能各自跑完——所以放进带兜底的混合步骤，而不是让模型自由决定怎么分批。
「每文件一组」只是退化兜底。 仅在分组失败 / 返回空 / 只有 1 个文件时才退到每文件一组。正常态下跨组、以及本次没变更的被依赖文件，都不共享巨型上下文，只能由子 Agent 用工具（⑤）按需取——分组是「按组隔离」能成立的前提。

03 · 实现 · 子 Agent流水线 ⑤/⑧ · 分而治之（按组） · 默认并发 8

每个文件组，一个隔离循环

  • 分发每个文件组独立 goroutine + 独立消息缓冲，组内文件共享同一上下文。受 --concurrency（默认 8）约束。
  • Plan（可选）双阈值触发：组内单文件最大变更 ≥ 50 行，或（文件数 ≥ 2 且组合计 ≥ 100 行）。单次 LLM，不发 Tools 字段；只读工具名以纯文本告知。
  • Main 循环外层评审轮次 MAX_REVIEW_ROUNDS 由 --effort 决定（low=1 / medium=2 默认 / high=3）；每轮内层工具调用上限 MAX_TOOL_REQUEST_TIMES（默认 100）。
  • 退出（5 条）task_done / 工具请求耗尽 / 连续 3 轮无有效工具结果 / context 取消 / 压缩压不回警告阈值。
为什么按组切

连贯 vs 效率

整 PR 塞进一个 Agent：上下文膨胀、信号稀释。切太碎（按 hunk）：看不到变更整体。语义分组是折中：相关文件捆进同一对话，结构强相关的依赖免费共享。跨组、以及本次没变更的被依赖文件，只能用工具按需取，不共享巨型上下文。

03 · 实现 · 行号流水线 ⑥/⑧ · 消除行号幻觉

模型不报行号；用 existing_code 片段回贴

  1. 1hunk 新侧：existing_code 对 context+added 做滑动窗口匹配 → 新文件行号

03 · 实现 · Prompt 拓扑横跨 ②–⑦ · 六个任务，不是一个万能提示词

把不确定性切成可替换的小面

Key何时做什么能否调工具
GROUPING_TASK分发前把变更文件聚成语义组（每组 ≤10）否（只喂文件元数据）
PLAN_TASK大 diff 前产出审查清单 → plan_guidance否（工具名纯文本）
MAIN_TASK主循环探索 + code_comment是（六工具）
MEMORY_COMPRESSION_TASK60%/80%摘要中间区否
RE_LOCATION_TASK行匹配失败重锚 existing_code否
REVIEW_FILTER_TASK循环后按 diff 证伪删评论否

模板在 task_template.json，占位符如 {{diff}}、{{system_rule}}、{{comments}}。改 prompt 需改模板并重建——这是故意的：审查流程不靠运行时随手改一句自然语言。

05 · 可迁移带走约束，不带走安装

任何要可追责的 Agent，都可以问这三句

01

能由程序保证的，不进提示词

文件进不进、规则用哪条、行号落哪一行。错了无法靠「再想一想」补救，就不要交给采样。

02

生成层后面，要有一层自己不能加戏的核查

只能删除被证据打脸的输出。不能改写成新结论。解析失败就原样保留。

03

核查层与生成层之间，要有信息边界

让核查者看到更少。同一模型也可以；挡住自我合理化的是看不见探索过程。

Rule-Guided Dispatch / filter-only / 信息不对称边界（论文 §3.2–§3.4）
